可以。建议你把修改分成 **4 层**：采集项扩展、CSV/预处理扩展、模型输入扩展、损失/AKF扩展。核心原则是：**目标量和控制补偿量作为输入，真值风仍作为监督标签；不要把 PX4 目标量当作标签。**

## 1. 数据集采集程序需要增加的数据项

当前采集项已经有：实际地速、空速标量、姿态、角速度、舵面控制、油门、真值风、转弯标签。

建议新增以下字段：

### A. PX4 目标/设定值

用于判断“飞机主动想这样飞”还是“飞控在抵抗风”。

建议字段：

```text
target_roll_deg
target_pitch_deg
target_yaw_deg

target_roll_rate_rad_s
target_pitch_rate_rad_s
target_yaw_rate_rad_s

target_velocity_north
target_velocity_east
target_velocity_down

target_airspeed_m_s
```

如果 MAVSDK 不直接提供这些目标量，建议用 MAVLink 消息读取：

```text
ATTITUDE_TARGET
POSITION_TARGET_LOCAL_NED
NAV_CONTROLLER_OUTPUT
TECS_STATUS / VFR_HUD
```

能拿多少先拿多少，最关键的是：

```text
目标姿态
目标角速度
目标速度或目标航迹
```

### B. 状态误差特征

这些可以采集时直接存，也可以预处理时计算。建议预处理时计算更稳。

```text
roll_error = roll_actual - roll_target
pitch_error = pitch_actual - pitch_target
yaw_error = wrap(yaw_actual - yaw_target)

roll_rate_error = p_actual - p_target
pitch_rate_error = q_actual - q_target
yaw_rate_error = r_actual - r_target

velocity_error_north = velocity_north - target_velocity_north
velocity_error_east = velocity_east - target_velocity_east
velocity_error_down = velocity_down - target_velocity_down
```

这些误差是“风被 PX4 补偿后的痕迹”，很重要。

### C. 实际舵面与执行器输出

当前如果只有 `roll_ctrl/pitch_ctrl/yaw_ctrl/throttle_ctrl`，它更接近控制指令。最好再记录实际执行量：

```text
aileron_actual
elevator_actual
rudder_actual
throttle_actual
```

仿真中可以从 JSBSim property 读实际舵面；真实机上可以读 servo output 或 actuator output。否则动力学损失会把“舵机延迟/限幅误差”误当成风。

### D. IMU 加速度

保留或新增：

```text
accel_body_x_m_s2
accel_body_y_m_s2
accel_body_z_m_s2
```

如果现在加速度是从速度差分出来的，建议优先记录原始 IMU 加速度，再在预处理中做滤波和重力补偿。

### E. 时间戳与有效性

每个异步数据源都建议加：

```text
xxx_valid
xxx_age_ms
```

例如：

```text
target_attitude_valid
target_attitude_age_ms
target_velocity_valid
target_velocity_age_ms
actuator_actual_valid
actuator_actual_age_ms
```

这样训练时可以避免 stale setpoint 污染样本。

## 最重要的设计结论

你的新数据项应该围绕这个逻辑组织：

```text
实际状态
+ 目标状态
+ 实际-目标误差
+ 控制输入/执行输出
+ 动力学模型
→ 反推出外部风扰动
```

标签仍然只需要真值风：

```text
wind_north, wind_east, wind_down
```

这样结构最清晰，也最符合“利用 PX4 补偿信息反推风场”的理论路线。

## 起飞稳定性补丁（2026-05-14，针对生产采集发现的级联崩溃）

### 背景：观察到的失败链

某次连续采集中观察到一段稳定复现的级联故障：

1. `[DataLogger] airspeed_m_s=nan 未就绪（airspeed_selector 仍在收敛），等待至多 30s`
2. 30s 后 airspeed 仍 NaN → 段内 0 有效点 → `validation/low_sample_rate`
3. SITL 重启后再次起飞，120s 内**飞机只到 0.9m**，但 `[Session] 起飞成功，高度=76.2m` 被打印
4. 几十秒后 `jsbsim_bridge: FGTable.cpp:511: Assertion 'Factor >= 0.0 && Factor <= 1.0' failed`
5. mavsdk_server 同步死亡，gRPC `Connection refused`

### 五个根因

| # | 根因 | 位置 |
|---|---|---|
| 1 | `arm_and_takeoff` 超时仅 `break` 不抛异常 | `flight_controller.py:379-381` |
| 2 | `_prepare_sortie_environment` 无条件打印"起飞成功" | `generate_dataset.py:483` |
| 3 | airspeed_selector 未输出有限值就放行起飞，TECS 给 0 油门 → JSBSim 攻角越界 | `_wait_telemetry_valid` 允许 nan airspeed |
| 4 | `_get_position_velocity_ned` 异常被 `except: pass` 静默吞掉 | `flight_controller.py:405-406` |
| 5 | `climb_descent` 兜底 `level_duration=10.0` 必然触发 `coverage_too_low` | `generate_dataset.py:602` |

### 修复细节

#### 1. `configs/runtime.yaml` + `lib/config/runtime.py`

`timeouts` section 新增 4 个字段，均带默认值：

```yaml
timeouts:
  airspeed_ready_s: 30
  airspeed_stable_s: 3
  position_stream_max_failures: 30
  climb_descent_event_grace_s: 8.0
```

#### 2. `flight_controller.py` —— 新增 `_wait_airspeed_selector_ready`

起飞前必经的 airspeed 选择器健康检查：要求 `airspeed_m_s` 连续 `airspeed_stable_s` 秒为有限值，否则抛 `FlightControllerError` 拒绝解锁。这是修复 JSBSim 崩溃的关键——TECS 拿到有限 airspeed 才会输出合理油门。

#### 3. `flight_controller.py::arm_and_takeoff` 重写监控循环

- 超时不再 `break`，而是抛 `TakeoffFailed(context={...})`，包含 `peak_alt_m / last_alt_m / consecutive_pv_failures` 等诊断字段；
- `_get_position_velocity_ned()` 异常**累计计数**，连续达到 `position_stream_max_failures`（默认 30 次≈30s）即抛 `TakeoffFailed`，避免 120s 静默空转；
- 所有阈值由调用方注入（来自 `runtime.yaml`），不再硬编码。

#### 4. `generate_dataset.py::_prepare_sortie_environment`

`arm_and_takeoff` 用 `try/except (TakeoffFailed, FlightControllerError)` 包裹，失败时通过 `StructuredLogger.warning("takeoff_failed", ...)` 写 jsonl，并 re-raise 让上层 sortie 切换到重启 SITL 路径。"起飞成功"日志只在真正完成后打印。

#### 5. `generate_dataset.py::execute_single_segment` (climb_descent 分支)

- `wait_for(altitude_reached.wait(), timeout=...)` 的超时从"整段时长 `duration`"收紧为 `min(duration, climb_time_est + grace_s)`，能更早检测事件未触发；
- 兜底 `level_duration` 不再硬编码 10s，而是 `max(duration - event_timeout, duration * min_coverage_ratio + 1.0)`，与 `quality_gates.min_coverage_ratio=0.6` 对齐——保证降级后仍可能通过 `coverage_too_low`；
- 兜底分支同步写 `StructuredLogger.warning("climb_descent_event_timeout", ...)`，便于事后分析。

### 测试

- `tests/run_all.sh` 全部 15 项 PASS；
- 新增 mock 集成测试覆盖三个失败路径：
  - airspeed nan → `FlightControllerError`（拒绝解锁）
  - 飞机停在 0.5m + 起飞超时 → `TakeoffFailed(context.last_alt_m=0.5)`
  - NED 流在预检阶段持续异常 → 预检层即拦截（双重防护）；起飞中失败的路径在代码审查中确认。

### 代理隔离加固（同期一并修复）

观察到的根因 7897 端口异常已经通过早先的 `no_proxy=localhost,127.0.0.1,::1` 修复
（最新日志显示连接的是真实端口 50051 而不再是代理端口 7897）。本次进一步加固：

#### 隐患

1. WSL 继承的 `NO_PROXY` 含 Windows 私有 token `<local>`，老版本 gRPC C-core 解析失败时会**整段忽略 NO_PROXY**；
2. `127.*` 通配符不被所有 gRPC 版本识别；
3. `HTTP_PROXY` 仍存在，会被 `subprocess.Popen` 启动的 mavsdk_server / PX4 SITL 子进程继承。

#### 三重保险

`generate_dataset.py` 顶部（grpc/mavsdk import 之前）：

- ① 显式置空 `HTTP_PROXY / HTTPS_PROXY / ALL_PROXY` 大小写六个变量；
- ② 设 `grpc_proxy=""` + `no_grpc_proxy="*"`（gRPC 专用控制变量）；
- ③ 用干净 token 重写 `no_proxy=127.0.0.1,localhost,::1,0.0.0.0`，移除 `<local>` / `127.*`。

`lib/infra/mavsdk_server.py` 与 `lib/infra/px4.py` 在 `subprocess.Popen` 时传入 `env=` 参数，
对子进程也独立做一次相同清理，**不依赖父进程的 env 继承**——即使将来有人在父进程之外另设环境变量，也不会影响子进程。

### airspeed_selector 检查的回调修正（同期发现的"过度严格"）

第一版修复把 airspeed_selector 检查放在**解锁前**，结果发现这与 PX4 的设计冲突：

- 地面静止时差压传感器 ΔP=0，PX4 的 `airspeed_validated` 输出 `nan` 是**合法的**；
- 必须等飞机离地、有相对气流后，airspeed_selector 才能输出有限值。

实战日志显示，第一版修复每次都在 30s 后抛 `FlightControllerError("airspeed_selector 未在 30s 内稳定")`，
**所有飞行都无法启动**。

修正方案：把 airspeed_selector 检查从"解锁前"挪到"起飞监控循环中"，且只在飞机已离地超过
`AIRSPEED_AIRBORNE_THRESHOLD_M = 15m` 后才生效。这样：

- 地面 nan：放行（PX4 设计行为）；
- 离地后 nan：开始计时，连续 `airspeed_ready_timeout_s` 秒仍 nan 才 abort；
- 离地后从 nan 收敛到有限：日志记录后清零计时器。

新增的 `_read_airspeed_safe()` 用 2s 超时单次读取 `fixedwing_metrics`，避免对正在监控的位置流造成阻塞。

旧的 `_wait_airspeed_selector_ready()` 方法保留（备用工具），但 `arm_and_takeoff` 不再调用它。

## 阶段 7（2026-05-14）：数据完整性根因修复（target_velocity NaN / IMU 全零 / Actuator 全零）

### 问题诊断

通过审查 `datasets-1-1` ~ `datasets-1-5` 共 5 段已采集数据（合计 50,566 条记录），发现三个字段族**几乎全程异常**：

| 字段族 | 现象 | 根因 |
|---|---|---|
| `target_velocity_north/east/down` | **99.99% NaN**（1 行有效） | PX4 NPFG fixed-wing 控制下 `POSITION_TARGET_LOCAL_NED` 的 `type_mask` 把 velocity 位标记为 ignore，对应 vx/vy/vz 字段填 NaN（MAVLink 协议）。`data_logger` 直接 `float(msg.vx)` 把 NaN 写入数据集 |
| `imu_accel_body_x/y/z` | **100% 全为 0**，`pymavlink_highres_imu_count=0` | PX4 默认 MAVLink stream 不发 `HIGHRES_IMU`（消息 ID 105），需要主动 `MAV_CMD_SET_MESSAGE_INTERVAL` 请求 |
| `aileron/elevator/rudder/throttle_actual` | **100% 全为 0**，`actuator_actual_valid=False` | `_sub_jsbsim_telnet` 连 `127.0.0.1:4560` 试图读 JSBSim Telnet，但 4560 是 jsbsim_bridge 的 mavlink TCP 端口（不是 Telnet）。`open_connection` 成功但 `readuntil(b"JSBSim> ")` 永远等不到文本提示符卡死 |

PI-GRU 的关键输入特征（IMU 加速度 + 实际舵面）全部缺失，对训练影响**严重**。

### 修复动作

#### 7.1 `data_logger.py`：POSITION_TARGET vx/vy/vz NaN 过滤

```python
elif mtype == "POSITION_TARGET_LOCAL_NED":
    vx_, vy_, vz_ = float(msg.vx), float(msg.vy), float(msg.vz)
    if not (math.isnan(vx_) or math.isnan(vy_) or math.isnan(vz_)
            or math.isinf(...)):
        self._target_velocity_ned = (vx_, vy_, vz_)
        ...
    else:
        self.stats["pymavlink_position_target_ignored_nan"] += 1
```

`_snapshot` 写入 entry 时增加二次 NaN 校验，确保即便某条 NaN 漏过 ingest，也不会进入数据集。

#### 7.2 `data_logger.py`：主动请求 HIGHRES_IMU 流

`_sub_pymavlink_targets` 在连接建立后立即发 `MAV_CMD_SET_MESSAGE_INTERVAL` (511) 请求：
- HIGHRES_IMU (msg id 105) @ 50Hz
- POSITION_TARGET_LOCAL_NED (msg id 85) @ 50Hz
- ATTITUDE_TARGET (msg id 83) @ 50Hz

幂等操作，即便 PX4 已默认发也不出错。

#### 7.3 `data_logger.py` + `runtime.yaml`：JSBSim Telnet 修复

- `runtime.yaml::ports.jsbsim_telnet` 由 4560 改为独立端口 6789；
- `_sub_jsbsim_telnet` 加入 `asyncio.wait_for(open_connection, timeout=1.5)` 和 `wait_for(readuntil, timeout=1.5)`，连接失败/不是 Telnet 时**静默退出**而非卡死；
- `DataLogger.__init__` 接受 `jsbsim_telnet_port` 参数，由 `generate_dataset.py` 从 `runtime.ports.jsbsim_telnet` 注入；
- `_snapshot` 增加 actuator_actual **回退路径**：当 `_actual_actuator=None` 但 `_actuator_ctrls` 已有值时，用 PX4 命令值代理：
  - `aileron_actual_rad = roll_ctrl × 0.35` (Rascal110 max aileron)
  - `elevator_actual_rad = pitch_ctrl × 0.30`
  - `rudder_actual_rad = yaw_ctrl × 0.35`
  - `throttle_actual_norm = clamp(throttle_ctrl, 0, 1)`
- 新增字段 `actuator_actual_source`：`"jsbsim_telnet" | "px4_command_proxy" | "none"`，便于训练脚本识别数据来源。

注意：`actuator_actual_valid` 仍为 False（代理值非真值），训练侧若严格要求 actual 可按 `valid` 过滤。要拿真实 fcs/* 值需在 `Rascal110-JSBSim.xml` 加 `<output type="SOCKET" port="6789" rate="100">` 节点（涉及 PX4 SITL 重新编译，本次未做）。

#### 7.4 IMU NaN 防御过滤（同 7.1）

`HIGHRES_IMU` 的 xacc/yacc/zacc 也加 NaN/Inf 过滤，避免极端情况下污染。

## 阶段 8（2026-05-14）：sortie 准备失败的鲁棒性修复

### 触发场景

第 3 次 sortie 起飞失败：`peak_alt=1.4m`，`last_alt=-12.86m`，`consecutive_pv_failures=19`，`last_err=TimeoutError`。这是 PX4 SITL/JSBSim 偶发的仿真停滞——飞机解锁后只升到 1.4 米就失去推力自由下沉，同时 PX4 不再发 LOCAL_POSITION_NED 消息，MAVSDK 的 NED 流连续 19 秒 RPC 超时。

`arm_and_takeoff` 正确识别了故障并抛 `TakeoffFailed`，但 Session 直接 re-raise 到顶层退出整个程序，**前面已采集的 3 段数据后面还有 2 段**因此被废弃（不是数据损坏，是没机会采）。

### 修复

#### 8.1 `_prepare_sortie_environment` 增加 sortie 级重试

抽出 `_prepare_sortie_environment_once` 为单次实现，外层 `_prepare_sortie_environment` 包裹 `runtime.retries.sortie_prepare`（默认 3）次重试循环。每次失败后：
- `stop_px4_sitl()` 清理进程
- `fc.disconnect()` 断开旧连接
- `sleep(segment_retry_backoff_s)`
- 下一轮重新写 wind_config + 启动 PX4 + 起飞

#### 8.2 Session 不再因单 sortie 失败终止整轮

`run_multi_segment_session` 调用 `_prepare_sortie_environment` 时捕获 `(TakeoffFailed, FlightControllerError)`：
- 记录 `sortie_skipped` 结构化错误（含被跳过的逻辑段编号）
- 清理 SITL/MAVSDK
- `continue` 进入下一个 sortie

已采集段不受影响（之前 datasets-1-1 / 1-2 / 1-3 已写盘）。

#### 8.3 配置新增

`runtime.yaml`:
```yaml
retries:
  sortie_prepare: 3   # sortie 准备整体最多尝试次数
```

`lib/config/runtime.py::RetriesConfig` 同步添加 `sortie_prepare: int = 3` 字段。

### 行为对比

| 情况 | 修复前 | 修复后 |
|---|---|---|
| sortie 1 起飞失败 1 次 | 整个 session 终止退出 | 重启 SITL 重试，最多 3 次 |
| sortie 3 连续 3 次起飞失败 | 整个 session 终止退出 | sortie 3 跳过，segments 4-5 标记缺失，session 继续到结束 |
| 已采集段数据 | 不丢（已写盘）但 metadata 不完整 | 不丢，结构化日志记录被跳过的段编号，便于补采 |
